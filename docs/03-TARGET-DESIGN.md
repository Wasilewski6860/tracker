# Целевая модель и архитектурные решения

Документ фиксирует правила развития. Раздел «Принятые решения» обязателен для кода. Остальное ниже — исходные предложения, на которых эти решения основаны.

## Принятые решения

Зафиксировано для этапа 0.

- Описание и комментарии хранятся текстом с небольшой разметкой: жирный, курсив, код, списки и ссылки `http`/`https`. HTML не исполняется, другие ссылки остаются текстом.
- Метка принадлежит проекту. Одинаковое название, без учёта регистра, — одна метка. Снятие метки с задачи не удаляет её из проекта. Наблюдатель метки не меняет.
- Вложение до 10 МБ хранится в отдельном каталоге под случайным ключом. Скачивание идёт через API с проверкой участия в проекте и заголовком, который не даёт браузеру открыть файл как страницу. Удаляет автор файла или владелец проекта. Программы, скрипты и HTML/SVG не принимаются.
- Процесс проекта настраивает владелец: название, категория, порядок статусов и переходы. Статус с задачами удаляется после выбора, куда их перенести. Хотя бы один статус категории «бэклог» остаётся, потому что новые задачи начинают с него.
- Иерархия: эпик содержит истории и задачи. История содержит задачи. Задача и ошибка содержат подзадачи. Эпик и ошибка не вкладываются. У подзадачи нет детей. Родитель из того же проекта. Циклы запрещены.
- Удаление задачи с вложенными запрещено. Сначала их переносят или удаляют. Внешний ключ родителя по-прежнему `ON DELETE SET NULL`, чтобы удаление всего проекта не упиралось в порядок строк; правило проверяет API под блокировкой строки.
- Связи: «связана с» (симметричная), «блокирует» и «дублирует» (направленные, с обратной формулировкой).
- Исключение участника снимает его с задач этого проекта в той же транзакции.
- Наблюдатель не создаёт, не меняет и не комментирует задачи. Удалить задачу может владелец проекта или её автор.
- Комментарий меняет только его автор. Удалить комментарий может автор или владелец проекта. Прежние события журнала не переписываются: правка и удаление добавляют новые.

## 1. Принципы

1. PostgreSQL и Backend — источник истины.
2. Frontend отвечает за отображение и пользовательский ввод, но не за обеспечение целостности данных.
3. Бизнес-операции, затрагивающие несколько таблиц, выполняются транзакционно.
4. Каждое изменение, важное для пользователя, отражается в истории.
5. Представления Board/List/Calendar/Timeline используют общую модель Issue.
6. Сначала простая и надёжная реализация; сложные Jira-функции вводятся только при наличии сценария.
7. Все изменения схемы БД — новыми миграциями.

## 2. Предлагаемая модель сущностей

### User
Пользователь системы. Содержит учётные данные и профиль. Email и пароль не должны попадать в публичные DTO без необходимости.

### Project
Проект с ключом, названием, описанием, владельцем/участниками и настройками. Ключ участвует в формировании человекочитаемого issue key.

### ProjectMember
Связь пользователя с проектом и ролью. Роли на первом этапе: owner, member, viewer. Точная матрица полномочий должна быть утверждена отдельно.

### Issue
Центральная сущность. Минимальные поля: project, number/key, title, description, type, status, priority, reporter, assignee, due date, parent, timestamps. Дополнительные поля подключать по мере необходимости.

### IssueLink
Связь между двумя задачами с типом. Для симметричных отношений отображение одинаково с обеих сторон; для направленных отношений UI показывает обратную формулировку.

### Comment
Комментарий с автором, датами создания/редактирования и телом. Удаление/редактирование должно быть отражено в активности согласно выбранной политике аудита.

### Activity
Неизменяемое событие о значимом действии: actor, issue, kind, payload, timestamp. Payload структурирован, UI формирует локализованный текст.

### Attachment
Метаданные файла, ссылка на задачу, автор, имя, MIME, размер, storage key и дата. Файловое содержимое хранится вне PostgreSQL.

### Status / Workflow / Transition
Статусы принадлежат проекту или схеме workflow; переходы определяют допустимые переходы. До реализации нескольких workflow можно оставить один workflow на проект.

### Label / Component / Version
Дополнительные классификаторы проекта. Labels — свободные/переиспользуемые метки; Components и Versions — управляемые сущности проекта.

### Sprint / Worklog / Watcher / SavedFilter
Дополнительные сущности следующих этапов. Не требуется вводить до соответствующих пользовательских сценариев.

## 3. Иерархия задач

Предлагаемая стартовая схема:

- Epic может содержать Story и Task.
- Story может содержать Task.
- Task может содержать Sub-task.
- Bug может быть самостоятельной задачей; возможность подзадач у Bug решить отдельно.
- Sub-task не может иметь детей.

Это не единственно возможная модель. Перед миграцией нужно утвердить правила для Bug, Epic и преобразования типов уже существующих задач.

Обязательные инварианты:

- Родитель и ребёнок принадлежат одному проекту (если межпроектная иерархия не будет отдельно спроектирована).
- Нет самоссылок и циклов любой длины.
- Родительский тип допускает тип ребёнка.
- У Sub-task есть допустимый родитель.
- Удаление/перемещение родителя не оставляет некорректное дерево.

## 4. Права доступа

Рекомендуется описать матрицу разрешений отдельно от UI. Минимальный набор действий:

- view_project / view_issue
- create_issue
- edit_issue
- transition_issue
- delete_issue
- comment_issue
- manage_members
- manage_project
- manage_workflow

Возможное начальное правило:

| Действие | Owner | Member | Viewer |
|---|---:|---:|---:|
| Просмотр проекта/задач | Да | Да | Да |
| Создание задач | Да | Да | Нет |
| Редактирование задач | Да | Да | Нет |
| Переход статуса | Да | Да | Нет |
| Комментарии | Да | Да | По отдельному решению |
| Удаление задачи | Да | Автор — по политике | Нет |
| Управление участниками | Да | Нет | Нет |
| Настройки проекта/workflow | Да | Нет | Нет |

Матрица является предложением. Серверная проверка обязательна для каждого endpoint.

## 5. Workflow

Workflow должен описывать:

- Набор статусов и их порядок в представлении.
- Категорию статуса (например, backlog / todo / in progress / done) для общих отчётов.
- Допустимые переходы.
- Возможность определить начальный статус для нового issue.

На первом этапе не нужны сложные validators, conditions и post-functions уровня Jira. Важно сделать управляемые статусы и переходы, не зашитые навсегда в код.

При изменении workflow нужно определить судьбу задач в удаляемом статусе: запретить удаление, перенести их в выбранный статус или архивировать статус.

## 6. История и транзакции

Для операций, меняющих данные задачи, запись Issue и Activity должна фиксироваться в одной транзакции. То же относится к созданию комментария и его activity event.

Событие должно хранить структурированные старое/новое значение, actor и timestamp. Не следует полагаться на текстовую строку, сформированную только на клиенте.

Для строгой аудируемости не перезаписывать старые события при редактировании; создавать новые события.

## 7. API и представления

- Списки должны поддерживать серверную фильтрацию, сортировку и пагинацию.
- Board не должна быть единственным endpoint, из которого можно получить задачи.
- Детали задачи должны загружаться отдельно от списка.
- Ответы API должны иметь согласованный формат ошибок.
- UI должен различать отсутствие данных, отсутствие прав, отсутствие сети и ошибку сервера.

## 8. Хранение вложений

Файлы хранить на отдельном volume или в совместимом объектном хранилище. В БД — метаданные и непрозрачный storage key. Скачивание проходит через API с проверкой доступа. Ограничить размер, типы файлов и частоту загрузки. Резервировать и БД, и файлы.

## 9. Эксплуатация

Для личного сервера достаточно одного Docker Compose deployment при условии:

- HTTPS reverse proxy.
- Секреты через env/secret management, не в Git.
- БД и SMTP не опубликованы наружу.
- Регулярные бэкапы вне основного сервера.
- Проверенное восстановление.
- Restart policy, healthcheck и ротация логов.
- Миграции выполняются контролируемо.

## 10. Не делать заранее

- Не строить микросервисы.
- Не вводить Kubernetes без реальной необходимости.
- Не делать универсальный конструктор workflow с десятками типов условий на раннем этапе.
- Не внедрять сложный JQL до стабильной модели фильтров.
- Не реализовывать все отчёты Jira до появления Sprint/Estimate/Worklog данных.
