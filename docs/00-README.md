# План развития Tracker

Документы описывают целевое развитие проекта в сторону персонального Jira-подобного таск-трекера. Продукт предназначен для личного использования и будет размещён на удалённом сервере. Поэтому приоритет — корректность данных, удобство ежедневной работы, безопасность публично доступного сервиса и простота сопровождения, а не enterprise-масштабирование.

## Состав документов

- [Технический backlog](01-BACKLOG.md) — задачи разработки с приоритетами, критериями готовности и зависимостями.
- [Аудит текущего состояния](02-CURRENT-STATE.md) — подтверждённые наблюдения по исходному коду и ограничения аудита.
- [Целевая модель и архитектурные решения](03-TARGET-DESIGN.md) — принципы, сущности и предлагаемые правила предметной области.
- [Дорожная карта](04-ROADMAP.md) — рекомендуемый порядок реализации.
- [Проверки и критерии приёмки](05-QUALITY-CHECKLIST.md) — сценарии регрессии, тестирования и готовности к серверу.

## Как пользоваться backlog

1. Сначала выполнить задачи P0, влияющие на целостность данных, корректность поведения и безопасность.
2. Не брать одновременно несколько крупных задач, меняющих одну и ту же модель данных.
3. Перед изменением схемы БД добавлять миграцию; не редактировать уже применённые миграции.
4. Для каждой задачи проверять критерии приёмки и добавлять тесты.
5. После каждого этапа обновлять этот backlog: отмечать выполненное, фиксировать новые обнаруженные проблемы и не считать задачу завершённой только потому, что интерфейс выглядит правильно.

## Приоритеты

- **P0** — блокирующая корректность, целостность данных или обязательная безопасность перед публикацией.
- **P1** — основная функциональность Jira-подобного продукта.
- **P2** — важное улучшение ежедневного UX и дополнительные представления.
- **P3** — расширенные и необязательные возможности.

Приоритет P0 не всегда означает, что задачу нужно выполнить до любой другой разработки: например, production hardening обязателен до публикации в интернет, но не блокирует локальную разработку.

## Границы соответствия Jira

Цель — близкие к Jira пользовательские сценарии и информационная модель, а не копирование всей Jira Software, её внутренних сервисов или enterprise-функций. Любое новое усложнение должно оправдываться реальной пользой для одного пользователя или небольшой личной команды.
