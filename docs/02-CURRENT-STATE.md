# Аудит текущего состояния

## Область проверки

Аудит выполнен по предоставленному архиву проекта. Проверены исходники API и Web, SQL-миграции, package scripts и Docker Compose. Визуальная оценка основана на структуре компонентов и CSS; полноценное ручное тестирование приложения в браузере и production-развёртывание не выполнялись.

## Технологический состав

- Web: React 19, TypeScript, Vite, React Router.
- API: Node.js, Fastify, TypeScript.
- База: PostgreSQL 16.
- Валидация: Zod.
- Авторизация: JWT и cookie-механизм.
- Развёртывание: Docker Compose, отдельные Dockerfiles и Nginx для Web.

Стек подходит для персонального проекта. Оснований переписывать приложение или менять основные технологии по результатам просмотра нет.

## Реализованные возможности, видимые в коде

- Регистрация, вход, подтверждение почты, сброс пароля.
- Проекты, участники и роли owner/member/viewer.
- Создание и просмотр задач типов epic/story/task/bug/subtask.
- Приоритеты low/medium/high/urgent.
- Исполнитель, срок и родительская задача.
- Доска со статусами и переходами.
- Комментарии и журнал активности.
- Приглашение зарегистрированных пользователей в проект.
- Базовые Docker-сервисы PostgreSQL, Mailpit, API и Web.

## Подтверждённые замечания по коду

### Иерархия

`apps/api/src/access.ts`: `assertParent()` проверяет наличие родителя в том же проекте и прямую самоссылку, но не проверяет циклы по цепочке предков. В `issues.ts` дополнительно проверяется наличие родителя у типа `subtask`, однако полной матрицы допустимых отношений типов нет.

`003_workflow.sql`: `parent_id` ссылается на `issues(id) ON DELETE SET NULL`. Это может оставить дочернюю задачу без родителя при удалении родительской.

### Связи задач

В `apps/api/src/routes/issues.ts` `relatedIssues()` возвращает ограниченный набор других задач проекта. Отдельной таблицы связей задач в миграциях нет. Это не реализует семантику Issue Links Jira.

### История

POST комментария вставляет запись в `comments`; в показанном обработчике нет вставки события в `activities`. Поэтому журнал активности не отражает добавление комментария.

### Доска и список задач

`apps/api/src/routes/projects.ts`, endpoint `/projects/:projectId/board`, выбирает задачи с `LIMIT 500`. По мере роста проекта старые задачи не попадут в ответ доски. В `ProjectPage.tsx` поиск и фильтрация выполняются по уже загруженному `board.issues`.

### Права

В `IssuePage.tsx` доступность действий на клиенте и серверные проверки должны быть согласованы. В частности, UI использует общий `canWrite`, тогда как серверное удаление дополнительно проверяет роль/авторство. Это создаёт риск отображения действия, которое сервер отклонит.

### Удаление участника

В `projects.ts` удаление участника удаляет запись `project_members`. `issues.assignee_id` ссылается на пользователя, а не на membership, поэтому назначенные этому участнику задачи могут сохранить его как исполнителя после исключения из проекта.

### Загрузка страниц

В `ProjectPage.tsx` эффект загружает данные при изменении `projectId`, но не отменяет предыдущий запрос и не проверяет, что ответ относится к актуальному проекту. Аналогичный сценарий следует проверить в `IssuePage.tsx`.

### Оптимистичное перемещение

В `ProjectPage.tsx` `move()` сохраняет снимок `previous`, оптимистично обновляет доску и при ошибке возвращает снимок целиком. При нескольких параллельных действиях полный откат может затереть более новое локальное состояние.

### API-клиент

`apps/web/src/api.ts` требует отдельной проверки обработки не-JSON ответов и сетевых ошибок. Следует различать 401 (нет авторизации) и временную недоступность API, чтобы ошибка сети не воспринималась как выход пользователя из системы.

### Production-конфигурация

В `docker-compose.yml` присутствуют dev-параметры: тестовые реквизиты PostgreSQL, placeholder JWT secret, `COOKIE_SECURE=false`, localhost URL, Mailpit и опубликованные порты PostgreSQL/Mailpit. Это конфигурация для разработки, не готовая для открытого сервера.

В Compose настроен healthcheck API по `/api/health`, но при production-подготовке следует удостовериться, что проверка отражает готовность критических зависимостей, включая БД.

### Зависимости и тесты

В package scripts API есть `dev/build/start`, Web — `dev/build/preview`; тестовых scripts в этих package.json нет. В архиве не обнаружена отдельная тестовая инфраструктура. В проверенной структуре не найден lock-файл приложения/корня, но способ установки зависимостей необходимо сверить с фактической корневой конфигурацией.

## Не подтверждено / требует отдельной проверки

- Реальное поведение всех экранов в браузере и адаптивность.
- Полный аудит безопасности JWT/cookie/CSRF, rate limiting и email flow.
- Наличие проблем компиляции: сборка в этом аудите не была подтверждена на чистом окружении.
- Производительность SQL под реальной нагрузкой.
- Корректность миграций на уже существующей БД с пользовательскими данными.
- Состояние Git history и наличие секретов в истории репозитория.
- Надёжность реального SMTP, TLS, reverse proxy и процесса восстановления резервной копии.

## Вывод

Текущий проект — разумный MVP с подходящим стеком и базовыми сущностями. Основной риск перед расширением — незавершённые бизнес-правила и целостность модели задач. Сначала следует закрыть P0 из backlog, затем наращивать Jira-подобные функции.
