# Технический backlog

Backlog сформирован по текущему исходному коду проекта. Формулировки «реализовать» означают, что функциональность в текущей версии отсутствует либо представлена упрощённо. Перед выполнением задачи необходимо повторно проверить актуальную ветку: код мог измениться.

Сделано в ядре: CORE-001, CORE-002, CORE-003, CORE-004, CORE-005, CORE-006, CORE-007, CORE-009, CORE-010, CORE-011. CORE-008: с доски снят скрытый предел в 500 задач; серверный поиск по всему проекту остаётся в JIRA-011. CORE-012: команда `npm test` проверяет иерархию, включая цикл в базе.

OPS-001…005: отдельный `docker-compose.prod.yml` без публикации базы и Mailpit, отказ стартовать с тестовым секретом, healthcheck базы, restart и ротация логов, сборка через `npm ci`, скрипты `npm run backup` и `npm run restore`. Проверенное восстановление на отдельной машине ещё впереди. JIRA-001: карточка делит чтение описания и поля справа; вложения ещё не сделаны. JIRA-002: автор правит свой комментарий, автор или владелец удаляет его, журнал получает отдельные события правки и удаления. JIRA-003: описание и комментарии показывают жирный, курсив, код, списки и безопасные ссылки; HTML остаётся текстом. JIRA-004: у задачи несколько меток проекта, повторное имя переиспользуется, доска фильтрует по выбранным меткам. JIRA-007: файл задачи хранится вне базы под случайным именем, скачивается только участником проекта и не открывается как страница. JIRA-008: владелец меняет статусы, их порядок и переходы; статус с задачами удаляется только после переноса, последний бэклог остаётся.

## P0 — целостность данных и исправление текущих дефектов

### CORE-001 — Защитить иерархию задач от циклов
**Область:** API, `apps/api/src/access.ts`.

**Проблема:** `assertParent()` проверяет существование родителя в проекте и прямое самоссылочное назначение, но не проверяет цепочку предков. Возможна циклическая иерархия из нескольких задач.

**Сделать:**
- При создании/изменении `parent_id` проверять, что назначаемый родитель не является потомком текущей задачи.
- Проверку выполнять транзакционно, с учётом конкурентных изменений.
- Возвращать понятную ошибку валидации.
- Продумать защиту от чрезмерно глубокой иерархии.

**Критерии приёмки:**
- Нельзя назначить задачу родителем самой себя.
- Нельзя создать цикл из двух и более задач.
- Корректная иерархия в несколько уровней обрабатывается согласно утверждённым правилам.
- Есть API-тесты на прямой и косвенный цикл.

### CORE-002 — Зафиксировать допустимую иерархию типов задач
**Область:** API, схемы БД, создание и редактирование задач.

**Проблема:** проверяется существование родителя и наличие родителя у `subtask`, но не проверяется допустимость комбинации типов. Например, текущая проверка не запрещает подзадаче иметь дочернюю задачу.

**Сделать:**
- Утвердить иерархию типов до реализации (предлагаемая модель в `03-TARGET-DESIGN.md`).
- Проверять тип родителя и тип дочерней задачи на Backend.
- Проверять изменение типа уже существующей задачи с учётом её детей и родителя.
- Не полагаться на скрытие неподходящих вариантов только в UI.

**Критерии приёмки:** все недопустимые комбинации отклоняются API; существующие допустимые данные не ломаются при миграции.

### CORE-003 — Определить поведение удаления родителя
**Область:** миграции, API удаления задач.

**Проблема:** `issues.parent_id` создан с `ON DELETE SET NULL`. При удалении родителя дочерние задачи сохраняются без него; для `subtask` это может нарушить правило «у подзадачи должен быть родитель».

**Сделать:** выбрать и задокументировать одно поведение: запрет удаления при наличии детей; удаление дерева с явным подтверждением; либо преобразование детей в самостоятельные задачи с корректировкой типа. Не оставлять неявное поведение FK единственным бизнес-правилом.

**Критерии приёмки:** API и UI показывают последствия удаления; после операции не остаётся некорректной иерархии; есть тесты для родителя с одним и несколькими уровнями потомков.

### CORE-004 — Исправить семантику связанных задач
**Область:** БД, API задач, `apps/api/src/routes/issues.ts`.

**Проблема:** `relatedIssues()` возвращает другие задачи проекта (ограниченный список), а не реальные связи. Пользователь может принять посторонние задачи за связанные.

**Сделать:**
- Добавить таблицу связей задач с типом связи.
- Определить направленные и симметричные типы связей.
- Запретить связь задачи с самой собой и дубликаты.
- Возвращать только реально связанные задачи и учитывать обратное отображение.
- Добавить UI добавления/удаления связей.

**Критерии приёмки:** связь сохраняется в БД, видна с обеих сторон согласно семантике типа, удаляется корректно; тесты покрывают дубликаты и самоссылки.

### CORE-005 — Включить комментарии в историю активности
**Область:** API, `comments`, `activities`.

**Проблема:** добавление комментария создаёт запись в `comments`, но не создаёт соответствующую запись в `activities`. Журнал задачи не отражает полный ход обсуждения.

**Сделать:** создавать комментарий и событие активности в одной транзакции; определить, как журнал показывает текст комментария и последующее редактирование/удаление.

**Критерии приёмки:** успешное добавление комментария отображается и в списке комментариев, и в журнале; при ошибке транзакции не остаётся половинчатого результата.

### CORE-006 — Устранить рассогласование прав на удаление задачи
**Область:** `apps/web/src/pages/IssuePage.tsx`, API.

**Проблема:** в интерфейсе доступность удаления определяется общим `canWrite`, тогда как Backend дополнительно проверяет авторство задачи или роль владельца проекта. В итоге кнопка может быть показана пользователю, запрос которого будет запрещён.

**Сделать:** определить единую матрицу прав для просмотра, создания, редактирования, перехода статуса, комментирования и удаления. Возвращать нужные возможности в DTO либо использовать единые правила на клиенте, не ослабляя серверную проверку.

**Критерии приёмки:** UI не предлагает заведомо недоступное действие; Backend остаётся окончательным арбитром; тесты проверяют owner/member/viewer и автора задачи.

### CORE-007 — Обработать удаление участника и его назначенные задачи
**Область:** `apps/api/src/routes/projects.ts`, БД.

**Проблема:** удаление участника удаляет membership, но назначенные ему задачи могут сохранить `assignee_id`, поскольку ссылка на пользователя не зависит от членства в проекте. При этом `assertAssignee()` запрещает назначать исполнителя, который не состоит в проекте.

**Сделать:** выбрать правило: снять назначение с задач; запретить удаление участника, пока есть назначения; либо сохранить историческое назначение, но явно разрешить отображение бывшего участника. Выполнить операцию атомарно.

**Критерии приёмки:** нет неожиданного «зависшего» исполнителя; UI и фильтры отображают состояние однозначно; есть тесты.

### CORE-008 — Убрать жёсткий лимит 500 задач из основной доски
**Область:** `apps/api/src/routes/projects.ts`, `ProjectPage.tsx`.

**Проблема:** endpoint доски выбирает не более 500 задач. Более старые задачи исчезают из этого представления, хотя общий счётчик проекта может учитывать больше.

**Сделать:** внедрить серверную пагинацию или загрузку по запросу; фильтры и поиск должны работать по всему проекту, а не только по первой загруженной порции. Для доски выбрать подходящую стратегию: лимит на колонку, виртуализация или отдельная подгрузка.

**Критерии приёмки:** все задачи доступны через предусмотренные представления; пользователь видит, что список неполный, если используется подгрузка; нет скрытого ограничения в 500.

### CORE-009 — Защитить загрузку данных от устаревших ответов
**Область:** `ProjectPage.tsx`, `IssuePage.tsx`.

**Проблема:** при быстрой навигации запрос предыдущего экрана может завершиться позже и обновить состояние уже нового экрана.

**Сделать:** использовать отмену запросов (AbortController) либо проверку актуальности запроса/идентификатора сущности перед применением результата.

**Критерии приёмки:** быстрые переходы между проектами и задачами не приводят к отображению чужих/устаревших данных; отменённые запросы не показывают ошибку пользователю.

### CORE-010 — Надёжно обрабатывать не-JSON и сетевые ошибки API
**Область:** `apps/web/src/api.ts`, `App.tsx`.

**Проблема:** клиент безусловно разбирает ответ как JSON. HTML-ответ reverse proxy, пустой ответ или сетевой сбой могут приводить к ошибке парсинга вместо понятного состояния. Проверку сессии нельзя трактовать как «пользователь не авторизован» при любой ошибке.

**Сделать:**
- Проверять статус ответа и Content-Type.
- Обрабатывать пустое тело, не-JSON, сетевые ошибки и таймаут.
- Различать 401/403, 4xx валидации, 5xx и отсутствие сети.
- Для недоступности API показывать отдельное состояние, не сбрасывая визуально сессию как при 401.

**Критерии приёмки:** сценарии 401, 403, 422/400, 500, 502, пустого ответа и offline отображаются корректно.

### CORE-011 — Защитить оптимистичные изменения доски от некорректного отката
**Область:** `ProjectPage.tsx`, функция `move()`.

**Проблема:** при ошибке перемещения состояние откатывается к снимку `previous`. Если параллельно пользователь выполнил другое изменение, откат может затереть более новое состояние.

**Сделать:** сериализовать переходы одной задачи либо использовать идентификаторы операций и адресный rollback; после ошибки синхронизировать данные с сервером.

**Критерии приёмки:** быстрые перемещения разных задач и повторные перемещения одной задачи не теряют подтверждённые изменения; при конфликте серверное состояние восстанавливается.

### CORE-012 — Добавить базовые автоматические тесты
**Область:** API и Web.

**Проблема:** в package scripts текущих приложений нет тестовых команд и в исходниках не обнаружена тестовая инфраструктура.

**Сделать:** выбрать минимальный стек тестирования; покрыть бизнес-правила API, авторизацию/роли, иерархию, workflow, комментарии, удаление и основные пользовательские сценарии.

**Критерии приёмки:** тесты запускаются одной документированной командой; CI/локальная проверка завершается ненулевым кодом при провале; критические бизнес-правила имеют регрессионные тесты.

## P0 — обязательная подготовка к публикации

### OPS-001 — Подготовить production-конфигурацию без секретов в Compose
**Область:** `docker-compose.yml`, `.env.example`, Dockerfiles.

**Проблема:** в Compose заданы тестовые значения БД/JWT, `COOKIE_SECURE=false`, localhost URL и Mailpit. Эти настройки не подходят для открытого сервера.

**Сделать:** вынести настройки в окружение; проверять обязательные production-переменные при старте; использовать сильные уникальные секреты; включить Secure Cookie за HTTPS; настроить реальный SMTP; не хранить реальные секреты в репозитории.

**Критерии приёмки:** production не стартует с известными дефолтными секретами/небезопасными настройками; пример env содержит только placeholders; секреты отсутствуют в Git.

### OPS-002 — Закрыть внутренние порты сервисов
**Область:** `docker-compose.yml`, Nginx/reverse proxy.

**Проблема:** PostgreSQL опубликован на хостовый порт 5433, Mailpit — на 8025 и 1025. Для production эти интерфейсы не должны быть публично доступны без явной необходимости.

**Сделать:** в production оставить доступ к БД и SMTP только внутри Docker-сети; наружу публиковать только reverse proxy/HTTPS; отделить dev compose от production compose.

**Критерии приёмки:** с внешней сети доступны только явно предназначенные публичные порты; приложение продолжает подключаться к БД и SMTP внутри сети.

### OPS-003 — Реализовать резервное копирование и проверку восстановления
**Область:** эксплуатация, PostgreSQL, будущие вложения.

**Сделать:** автоматический `pg_dump`, расписание, ротацию копий, хранение вне основного сервера, документированную процедуру восстановления; включить вложения в резервное копирование после внедрения файлового хранилища.

**Критерии приёмки:** есть свежая копия; восстановление проверено на отдельной БД/окружении; документированы RPO/RTO на разумном для личного проекта уровне.

### OPS-004 — Повысить надёжность Docker Compose
**Область:** `docker-compose.yml`, Dockerfiles.

**Сделать:** добавить restart policy; настроить ротацию логов; запускать процессы без root, где возможно; добавить корректные healthcheck; проверить порядок миграций; не считать API здоровым, если критически недоступна БД.

**Критерии приёмки:** перезапуск хоста/контейнеров не требует ручного вмешательства; healthcheck отражает готовность приложения; логи не растут бесконечно.

### OPS-005 — Зафиксировать зависимости lock-файлами
**Область:** npm workspace/приложения, Docker build.

**Проблема:** в предоставленной структуре не обнаружен корневой или app-level `package-lock.json` (при этом в `node_modules` есть служебный lock-файл). Точные команды установки нужно согласовать с фактической конфигурацией репозитория.

**Сделать:** определить единый способ управления зависимостями; сохранить lock-файл; использовать `npm ci` в воспроизводимой сборке.

**Критерии приёмки:** чистая установка и сборка воспроизводимы на чистом окружении.

## P1 — функциональная основа Jira-подобного продукта

### JIRA-001 — Полноценная карточка задачи
Добавить структурированные секции: summary, description, тип, статус, приоритет, reporter, assignee, сроки, родитель, подзадачи, связи, комментарии, журнал, вложения. Разделить редактирование и чтение, обеспечить понятную компоновку и сохранение.

**Приёмка:** карточка не теряет данные при переключении секций; поля доступны по ролям; изменения отражаются в журнале.

### JIRA-002 — Редактирование комментариев
Добавить редактирование/удаление комментария с правилами доступа и фиксацией событий в журнале. Уточнить, может ли редактировать только автор, владелец проекта или оба.

### JIRA-003 — Форматированный редактор описания и комментариев
Поддержать согласованный формат (например, Markdown или rich text). Безопасно очищать/рендерить содержимое; не допускать XSS. Сохранить читаемость обычного текста.

### JIRA-004 — Метки (Labels)
Добавить множество меток на задачу, автодополнение существующих меток проекта, фильтрацию и управление.

### JIRA-005 — Компоненты проекта
Добавить компоненты с ответственным/описанием при необходимости; назначать компонент задачам; фильтровать по компонентам.

### JIRA-006 — Версии и релизы
Добавить версии проекта, статусы релиза и поля Fix Version / Affects Version. Не вводить сложный релизный процесс, пока он не нужен.

### JIRA-007 — Вложения
Реализовать загрузку, скачивание и удаление вложений; хранить метаданные в БД, файлы — в отдельном volume или объектном хранилище. Проверять размер, MIME/type, имя, права доступа и содержимое. Не отдавать файлы как публичные статические URL без проверки прав.

### JIRA-008 — Настраиваемые статусы и workflow
Перенести статусы и переходы из фиксированной схемы в редактируемую конфигурацию проекта. Реализовать создание/переименование/архивирование статусов, порядок колонок и переходы. Не позволять удалить статус, пока в нём есть задачи, без стратегии переноса.

### JIRA-009 — Единая история изменений
Сделать единый формат событий для изменения полей, статусов, комментариев, связей, вложений и назначений. Хранить actor, timestamp, тип события и структурированный payload. Сортировка должна быть стабильной при совпадающих timestamp.

### JIRA-010 — Уведомления и watchers
Добавить подписку на задачу и уведомления о назначении, упоминании, комментарии и важных изменениях. Для личного продукта предусмотреть настройки частоты/отключения уведомлений, чтобы не создавать шум.

### JIRA-011 — Глобальный поиск и фильтры
Добавить поиск по проектам/задачам с серверной фильтрацией по ключу, названию, статусу, типу, приоритету, исполнителю, автору, сроку и меткам. Не ограничивать результаты уже загруженной доской.

### JIRA-012 — Сохранённые фильтры
Позволить сохранять набор условий и повторно открывать его; определить приватность фильтра и возможность делиться им внутри проекта.

### JIRA-013 — Редактирование проекта
Добавить изменение названия, описания и других безопасно изменяемых настроек. Изменение ключа требует отдельного решения из-за влияния на issue key и внешние ссылки.

### JIRA-014 — Массовые операции
Добавить множественный выбор задач и массовое изменение поддерживаемых полей с предварительным просмотром и отчётом об ошибках.

Добавить даты, цель спринта, состав задач, старт/завершение и обработку незавершённых задач. Проверить правила переноса задач при завершении.

### VIEW-004 — Calendar
Показывать задачи по due date; поддержать переход к задаче и фильтрацию. Чётко различать срок выполнения и даты спринта.

### VIEW-005 — Timeline / Roadmap
Показывать задачи/эпики на временной шкале; для задач без дат предусмотреть понятное поведение; не придумывать даты автоматически.

### VIEW-006 — Dashboard
Создать настраиваемую главную страницу с гаджетами: мои задачи, просроченные, распределение по статусам/приоритетам, недавняя активность.

### VIEW-007 — Настройки представлений
Сохранять предпочтения доски/списка: фильтры, порядок, видимые поля, возможно ширину колонок. Разделить персональные настройки и настройки проекта.

### UX-001 — Единая дизайн-система
Унифицировать типографику, отступы, цвета, радиусы, размеры контролов, состояния hover/focus/disabled/loading/error. Ориентироваться на актуальный Jira UI, не копировать случайные детали разных версий.

### UX-002 — Системные уведомления и состояния
Добавить Toast, skeleton, empty state, error state, подтверждение опасных операций, индикацию сохранения и предупреждение о несохранённых изменениях.

### UX-003 — Улучшить навигацию
Добавить контекстную навигацию проекта и быстрый доступ к проектам, задачам, фильтрам и дашборду. Не перегружать интерфейс редко используемыми пунктами.

### UX-004 — Диалоги и доступность
Заменить нативные `confirm()` собственными диалогами; реализовать управление фокусом, Escape, возврат фокуса, доступные labels и keyboard navigation.

### UX-005 — Быстрые действия
Поддержать быстрый переход к задаче по ключу, создание задачи из контекста, клавиатурные shortcuts после их документирования.

## P3 — расширенные функции

- **EXT-001 Worklogs:** учёт затраченного времени, оценка, remaining estimate.
- **EXT-002 Automation:** правила вида trigger-condition-action с историей выполнения и защитой от циклов.
- **EXT-003 Import/Export:** CSV/JSON экспорт и контролируемый импорт с предварительной проверкой.
- **EXT-004 Archive/Trash:** архивирование проектов/задач и восстановление вместо необратимого удаления по умолчанию.
- **EXT-005 JQL-подобный язык:** только после стабилизации фильтров и поиска.
- **EXT-006 Дополнительные issue types:** например, Epic/Story/Task/Bug/Sub-task уже поддерживаются; расширять только при реальной потребности.
- **EXT-007 Отчёты:** velocity, burndown и другие Scrum-отчёты после появления корректной модели спринтов и оценок.

## Технические долги и вопросы для отдельного решения

- Уточнить матрицу ролей owner/member/viewer и права автора задачи.
- Уточнить, должна ли система поддерживать одного пользователя или несколько пользователей/участников.
- Решить, нужна ли регистрация по email в долгосрочной личной инсталляции или достаточно закрытой регистрации/приглашений.
- Определить политику хранения/удаления истории.
- Проверить все SQL-запросы на индексы и отсутствие N+1 при росте данных.
- Проверить `.env`, `.gitignore` и историю Git на случайно закоммиченные секреты. Не копировать реальные значения секретов в документацию.
